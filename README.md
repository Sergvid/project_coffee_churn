# Прогнозирование оттока клиентов сервиса доставки кофе

Бинарная классификация на сильно несбалансированных данных с подбором
порога решения и упаковкой модели в продакшен-пайплайн.

## Задача

Удержать существующего клиента дешевле, чем привлечь нового. Кофейня
накапливает данные о поведении клиентов, но не знает заранее, кто из них
собирается уйти.

Требовалось построить модель, которая по поведенческим признакам выявляет
клиентов с высоким риском оттока, чтобы маркетинг успел запустить
персональные предложения до того, как клиент уйдёт.

Дополнительное требование: модель должна быть интерпретируемой — бизнесу
важно понимать не только кто уйдёт, но и почему.

## Данные

10 450 клиентов, 27 признаков:

- поведение: частота и сумма заказов, дни с последнего заказа, средний чек
- предпочтения: тип кофе, обжарка, молоко, размер напитка, происхождение зёрен
- приложение: открытия в неделю, уведомления, сбои
- лояльность: подписка, использование скидок, промо-акции
- прочее: сезон, геолокация, тип устройства, оценки

Целевая переменная `churn`: **6% ушедших против 94% оставшихся** — сильный
дисбаланс, который определил выбор метрики.

Пропуски присутствуют во всех признаках (от 1 до 9,5%).

*Данные предоставлены в рамках учебного проекта и в репозиторий не включены.*

## Стек

Python, pandas, NumPy, scikit-learn, joblib, Matplotlib, Seaborn

## Ход работы

1. Разведочный анализ: дисбаланс классов, пропуски, выбросы, корреляции,
   связь категориальных признаков с оттоком
2. Кастомные трансформеры для генерации признаков и обработки выбросов
3. Стратифицированное разбиение 80/20, сборка пайплайна предобработки
4. Обучение базовой модели с кросс-валидацией
5. Feature engineering: 10 новых признаков, интерпретация коэффициентов,
   отбор значимых
6. Подбор гиперпараметров через `GridSearchCV`
7. Подбор порога решения на кросс-валидации через `cross_val_predict`
8. Финальная оценка, сохранение артефактов, проверка воспроизводимости

## Результат

| Метрика | Кросс-валидация | Тест |
|---|---|---|
| **PR-AUC** | **0,713 ± 0,024** | **0,673** |
| F1 | 0,602 ± 0,041 | 0,608 |
| ROC-AUC | 0,935 ± 0,016 | 0,932 |
| Precision | 0,829 ± 0,022 | 0,637 |
| Recall | 0,476 ± 0,054 | 0,581 |

При базовом уровне PR-AUC 0,060 (доля положительного класса) модель
превосходит случайный классификатор **в 11 раз**.

Итоговая конфигурация: `LogisticRegression(C=0.1, penalty='l1',
solver='saga', class_weight=None)`, порог решения 0,35, 38 признаков из 53.

Прогресс по этапам работы:

| Этап | CV F1 | Test F1 | ROC-AUC |
|---|---|---|---|
| Baseline (Dummy) | 0,000 | 0,000 | 0,500 |
| Базовая логистическая регрессия | 0,430 | 0,430 | 0,920 |
| + новые признаки | 0,455 | 0,438 | 0,928 |
| + подбор гиперпараметров | 0,609 | 0,563 | 0,933 |
| + подбор порога | 0,602 | **0,608** | 0,932 |

## Ключевые находки

**Главная причина оттока оказалась технической, а не маркетинговой.**
Признак `app_crashes_last_month` показал корреляцию с оттоком 0,50 — на
порядок выше всех остальных, — и наибольший коэффициент в модели (+1,98).
Клиенты уходят не потому, что им не нравится кофе, а потому, что падает
приложение. Это меняет адресата рекомендаций: работать нужно команде
разработки, а не отделу маркетинга.

**Подписчики уходят чаще, чем клиенты без подписки.** Доля оттока среди
пользователей тарифа `pro` — около 13%, среди клиентов без подписки — около
5%. Результат контринтуитивный: обычно подписка считается признаком
лояльности. Вероятное объяснение — завышенные ожидания premium-сегмента,
которые сервис не оправдывает.

**Подбор порога дал больший прирост, чем подбор гиперпараметров.** При
стандартном пороге 0,5 модель находила лишь 44% уходящих клиентов, при
том что PR-AUC был уже высоким. Проблема была не в качестве модели, а в
решающем правиле: для класса с долей 6% порог 0,5 слишком консервативен.
Снижение до 0,35 подняло recall с 0,44 до 0,58 — модель стала находить
72 уходящих клиента вместо 54 из 124.

**Выбор рабочей точки — управленческое решение.** PR-кривая показывает
несколько сценариев:

| Стратегия | Порог | Precision | Recall |
|---|---|---|---|
| Высокая точность | ~0,50 | 0,79 | 0,44 |
| Баланс | 0,35 | 0,64 | 0,58 |
| Широкий охват | ~0,20 | 0,40 | 0,85 |

Выбран баланс: из каждых десяти предупреждений шесть указывают на реально
уходящего клиента при охвате 58% оттока.

**Балансировка классов не понадобилась.** `class_weight='balanced'`
стабильно проигрывал варианту без балансировки на всех конфигурациях
GridSearchCV. Причина в том, что дисбаланс уже учтён выбором метрики
(PR-AUC и F1 по редкому классу), а принудительная балансировка жертвовала
precision ради recall — то, чем лучше управлять напрямую через порог.

## Что было самым сложным

Защита от утечки данных при обработке выбросов. Границы IQR для обрезки
экстремальных значений нельзя считать по всему датасету: тогда статистика
тестовой выборки повлияет на преобразование обучающей. Реализован кастомный
трансформер `OutlierClipper` на базе `BaseEstimator` и `TransformerMixin`,
который запоминает границы на `fit` (только по train) и применяет их на
`transform`. Аналогично устроен `FeatureEngineer`, генерирующий 10
производных признаков.

Второй нетривиальный момент — подбор порога. Соблазн подобрать его прямо на
тестовой выборке велик, но это превратило бы тест в часть процесса обучения
и завысило оценку. Порог подобран через `cross_val_predict` на обучающих
данных, а тест использован ровно один раз. Расхождение метрик CV и теста
оказалось минимальным (PR-AUC 0,713 против 0,673), что подтверждает
корректность подхода.

Отдельного внимания потребовали отрицательные значения в
`total_spent_last_week` — физически невозможные траты. Такие строки удалены
до разбиения, поскольку речь идёт об очевидных ошибках данных, а не о
преобразовании, зависящем от статистики выборки.

## Рекомендации бизнесу

1. **Исправить сбои приложения** — прямое воздействие на главный фактор
   оттока. Техническая проблема даёт больший эффект, чем любые
   маркетинговые акции.
2. **Запускать промо для клиентов, давно не получавших предложений** —
   признак `days_since_last_promo` вошёл в число значимых.
3. **Разобраться с оттоком premium-сегмента** — подписчики `pro` уходят
   в 2,5 раза чаще остальных, что требует отдельного исследования.
4. **Использовать модель для еженедельного скоринга** с порогом 0,35 и
   передачей списка в кампанию удержания.

## Подготовка к внедрению

Сохранены артефакты для эксплуатации:

- `full_model_pipeline.pkl` — единый пайплайн: генерация признаков,
  обработка выбросов, заполнение пропусков, кодирование, модель
- `threshold.pkl` — подобранный порог решения
- `feature_engineering.py` — модуль с функцией генерации признаков

После загрузки проверено полное совпадение предсказаний с исходной моделью.

Использование сводится к двум строкам:

```python
prob = pipeline.predict_proba(X_new)[:, 1]
pred = (prob >= threshold).astype(int)
```

На вход подаются сырые данные клиента — все преобразования выполняются
внутри пайплайна.
